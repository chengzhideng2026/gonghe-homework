# 统计实验接口复盘（先只读旧轨迹）

复盘起点 `2e53f12ee1042260e871eb7ff4e11e5f6cf098c7`。本节结论仅来自代码和原四次轨迹，没有新增模型/ERP调用。原失败和原报告保留；此前把问题概括成“模型引用错误ID”不完整，接口本身也有缺陷。

## 明确接口缺陷

1. get_document/get_documents 的实际返回正文只有 ok/data/io，正确来源 ID 不在正文，未提供可复制的 evidence_ref；它仅出现在 assistant.tool_calls[].id、tool.tool_call_id 协议字段和客户端收据/trace。客户端确实把协议字段发给供应商，所以**不能声称整个请求没有ID，也不能证实供应商把ID隐藏了**。可确认的是：参数要求依赖协议 ID，却没有在工具业务正文建立显式引用约定。D02两个猜测ID被拒绝、D01改用calculate，都与此缺口一致。旧离线 ask 测试预先知道 mock ID，未验证模型只凭正文能取得所需引用。
2. 系统规则要求每个比例调用calculate，新工具描述又要求明细统计优先summarize_details，存在重叠且不一致的指导。应只针对这两个计算工具明确等价的确定性计算通道，不能强迫所有小任务换工具。

## 合理的原工具选择与参数评估

两组只有4/5条匹配行，calculate已经能正确求和与加权平均；三次calculate在同一个assistant响应中发出，实际上只占一次计算编排轮，而不是三次模型请求。新工具不能仅凭“3个工具变1个”就宣称减少了模型轮数。其具体价值在于直接绑定子行证据、统一重复行/币种/单位处理，以及一次给出计数、极值和Decimal舍入；旧描述已列出这些场景，不是完全没有用途说明。

新工具**没有要求重填DocType、父单名、日期范围、币种或单位数值**：这些来自读取快照。fields是可选映射，两个旧真实调用均未传它。table_field用于选择父单的某个子表；父单往往有多个表，不能不经确认默认选items。row_equals也必要：父单筛选命中一个物料后，全文仍包含其他物料行，不能删除行筛选或把父单过滤等同子行过滤。显式选择来源用于消除多次读取歧义，需要保留，但应改成正文公开的简短引用，而不是猜协议ID。

## token增长：实测、重建与不能确认的部分

逐轮供应商usage和重建的消息字节数见 [只读审计数据](evidence/interface_readonly_audit.json)。以下字节数为使用相同json.dumps设置重建的messages/工具定义大小，不是token估算，也不是原始HTTP包抓取；四条历史均未裁剪，usage事件与assistant响应一一对应。

- 八工具定义7119字节，九工具8619字节，增加1500字节。两组第一轮消息分别完全相同，原版→实验的prompt tokens均增加335（3512→3847、3513→3848），与新增工具定义对应；不能进一步精确拆分供应商内部模板/tokenizer开销。
- D01输入46613→37408，输出1532→1622，总量48145→39030。实验少了错误聚合的两轮，读取同样4张全文，工具正文均21778字节；没有证据表明新统计工具贡献了节省。
- D02输入29057→74624（+45567），输出2004→1914（-90），总量31061→76538。原版使用3188字节的关联子字段列表，实验读取5张父单全文，正文27330字节。全文返回后，实验第三轮输入15865 tokens，后续三轮16218、16525、17514，持续重发这批全文和新增消息。两次引用失败让这些大上下文继续重复，最终仍回退calculate。
- 合计增加36362 tokens，全部体现为prompt总量增加，completion合计恰好相等。不能把差额都算成“思考更多”；供应商另报reasoning_tokens，不能和completion_tokens重复相加。cached_tokens也保留，但不把缓存命中误当作没有输入token或据此推算费用。

可以确认数据路径更大、失败轮重复上下文、定义变大。不能确认每条消息各自贡献多少token、供应商是否隐藏协议ID、去掉ID问题后模型必然选择新工具、单次耗时差异是否稳定；这些均是未验证假设。不能统一归因于“模型不会用”。

## 最小修复与最后一组预算

仅在实验分支把成功父单读取的短 evidence_ref 放入工具返回正文，内部继续绑定实际协议call_id、工具版本、参数、返回数据、io时间和覆盖范围；来源必须显式选择，不默认最近一次。统计参数改为evidence_refs，其余必要字段选择和行筛选保留。来源拒绝、去重、部分读取及分区检查不放宽。计算规则仅允许这两个计算工具在其支持范围提供计算证据。

先做离线协议测试：从真实出站请求的工具正文复制ref，不访问客户端内部字典/协议ID；覆盖多来源、错误/旧引用、部分成功和范围保持。只有通过后，按 [最后一组冻结计划](interface_pair.json) 对**原D02原文**新增一次原版和一次修复版比较。不新增问题、不提高预算、不重跑择优；新旧记录分开。原已交付分支不变。

## 已实施的最小修复与离线验证

修复运行版本：`ff5852acb41e9b8ee70a02390fafeeb69e14c05a`。仅实验分支修改：

- 成功get_document/get_documents的返回正文增加顶层evidence_ref，例如本次真实返回的 `e57ccfaf9_1`。引用由程序生成，绑定当前轮的实际call_id、工具版本、原参数、完整返回值及io时间，旧轮和未知引用均拒绝。

### 归因与剩余限制

**明确修复效果：**公开引用出现在模型实际收到的正文中，并被正确使用；本次无来源错误、无需calculate回退。原来源保护没有为了通过而放松。这支持接口缺陷修复有效，不能反向断言供应商之前一定隐藏了协议ID。

**合理工具选择：**原版calculate也算对，三次调用仍在一个响应中。修复版主动重复填了六个默认fields映射，这些是可选而非必需；尚有接口使用冗余，本轮不继续调参。新工具返回来源、范围和父单观察，比三个简短calculate结果也有更多正文成本。

**不能全部归给统计工具的收益：**本次原版另外读取元数据（1 HTTP）并做一次失败聚合（2 HTTP），修复版没有；差3次ERP请求有明确查询路径差异。原版元数据使第二轮messages达到47592字节，后续保留全文后达到84605字节，并出现over_budget=true（当前轮84212字节）；预算没有被提高，继承的当前轮超预算限制没有在此扩展修复。修复版最后一次messages49358字节。输入token下降包含元数据/失败查询/重复上下文路径差异，不能将39460个总token节省或5.986秒差额全归为“一次统计替代三次算术”。

逐轮还可以明确定位：本次原版先单独用一轮获取metadata，随后一轮同时aggregate+list，再get、calculate、回答；修复版是list、get、summarize、回答。因此两版的计算编排均为一轮，少1次模型请求对应于少了前置metadata轮，**本组没有证明统计工具本身减少模型往返**。

旧实验D02可作历史故障参照：同样7次ERP请求，来源错误2→0、成功统计0→1、模型6→4、总tokens76538→44400。它支持公开引用解决了实际失败路径，但不是另一次新配对或稳定性验证。尤其首次原版D02为31061 tokens，本次原版为83860，修复版44400介于两者之间；查询规划波动很大，不能择取这次较贵的原版后宣称工具普遍更省。

**判断：**接口可用性缺陷已修复并完成一组真实验证，旧实验的失败不能笼统归因为“模型不会用”。整体效率仅有单组观察，不能据此宣称普遍或稳定收益。两版核心数字有证据支持；原版均价表格写USD时应更准确标USD/Nos，两版仍多列了未要求的明细，不宣称严格精简回答或完整业务验收通过。本人操作验证未执行。到此结束，保留实验分支，不推送、不合入main-v2、不修改已交付版本。
