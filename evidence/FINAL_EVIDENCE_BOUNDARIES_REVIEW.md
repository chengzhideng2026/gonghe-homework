## 修改与通用正反例

`agent.py` 用 v2 证据边界规则替换精确匹配的旧 v1 块，保留其他系统规则；不会每轮重复追加。规则区分 ERP 事实、用户条件和程序计算。用户报价可用于明确标注来源的条件计算，不要求重复证明其已经提供的币种；空主档只说明读取范围内的空字段。

付款策略要求先缩小相关父单，再用通用读取核对已提交状态、`references.reference_doctype/reference_name/allocated_amount`；不能以 `reference_no` 替代核销，也不能以整笔 `paid_amount` 代替每张发票分配额。缺字段、权限失败、草稿和空子表仍分别报告。`erp_tools.py` 在 Payment Entry 列表正文中增加同样的证据警告，并对 Bin 预留增加仓级归属警告；没有扩大读取范围或自动发起额外请求。

`answer_checks.py` 保留原 ERP 币种检查，新增有明确来源标注的用户金额路径：

- 直接引用须匹配用户实际输入的币种和数值，不把该币种加入 ERP 证据集合。
- 推导金额须匹配当前轮成功 `calculate` 的结果，且表达式包含对应用户金额输入；混合用户币种不由此路径放行换汇。
- 已明确标注为上一轮来源的用户条件可以复用，推导仍需要当前计算；旧轮 ERP 币种、旧计算和程序修正提示不能冒充本轮证据。
- 已有采购预览处理器算出的 Decimal 总额可直接引用，不强制重复 `calculate`。报价来源识别不会改变采购工具的报价币种和本位币校验。

Markdown 检查仅处理连续的表头、匹配列数的分隔行和数据行；标题、正文、空行、列数不匹配和新表头终止当前表。下一张表按自身列位检查。缺必要列或分隔行时不假定已完成核验；单位列不能误当数值列，明确混合单位仍拦截；代码围栏内示例不视为渲染表格。

## 实际边界与交付状态

本轮的付款核销与工单归属修复是通用策略及工具正文警告，不是新增的语义证明器。原 FNL-07 错误正文不能被现有 `evidence_issues` 当作任意自然语言核销错误自动证明；需要独立模型验证其是否按策略取得并忠实引用子表。H08 的全局无记录推断也依赖模型遵循范围规则。

币种检查是有限的来源门槛，用户引用依赖明确归因和字面值匹配，计算路径不是完整的单位/量纲分析。原 ERP 币种路径也不证明同轮任意单据、金额之间的精确对应关系。未支持的表达方式可能需要修订措辞；不能称为通用事实证明。Markdown 检查支持此处测试的简单结构，不宣称覆盖所有 Markdown 扩展。

程序检查通过不等于真实模型或本人业务操作验证通过。本轮没有新的真实模型验收结果；旧独立报告中的 PASS/PARTIAL/FAIL 均保留，不能混入本候选成绩。完成敏感信息检查后正常推送同一分支并更新 PR #4，不合并 `main-v2`，停止开发，等待独立评测。
